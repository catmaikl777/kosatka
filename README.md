# 🐋 Косатка Клик (PIXEL ORCA)

Пиксель-арт кликер с живым мультиплеером: PvP-дуэли и рейды 3×3 между настоящими игроками,
кланы, сезонный ивент и полностью рабочий офлайн-режим.

Клиент — статические файлы без сборки и без зависимостей. Сервер — один файл на Node.js
(стандартные модули, WebSocket написан вручную по RFC 6455), внешних npm-пакетов нет.

---

## Быстрый старт

```bash
# 1. Только игра (работает офлайн, PvP — с ботом)
python3 -m http.server 8080
# открыть http://localhost:8080

# 2. Игра + живой мультиплеер
node server/server.js
# клиент: http://localhost:8080   сервер: http://localhost:8081
```

Клиент сам подключается к `/ws` того же хоста. Чтобы указать другой сервер, задайте
глобальную переменную **до** подключения клиента:

```html
<script>window.PO_SERVER = 'wss://orca.example.com/ws';</script>
```

Если `PO_SERVER` не задан или сервер недоступен, игра честно переходит в офлайн:
накопленный доход считается по времени отсутствия, а в PvP появляется кнопка
«БОЙ С БОТОМ». Симулировать соперников в сетевом режиме нельзя — только живые игроки.

## Что внутри

| Возможность | Детали |
|---|---|
| Кликер | криты, множители, апгрейды кликов/монет/дохода, пассивный доход |
| Прогресс | достижения, квесты (daily), боксы, рыбалка, магазин скинов |
| Престиж | сброс слоя с бонусами и «очками силы» |
| Аккаунты | регистрация/вход по паролю, PBKDF2 + соль, токены устройств |
| Облако | сейв на сервере, восстановление по токену, диалог «локально или облако» |
| Кланы | создание, код приглашения, роли, казна и бонус к доходу |
| PvP | лобби (открытые/закрытые/по коду), дуэли на время, награды и билеты |
| Рейды | команды 3×3, поиск соперника, общий счёт команды, награды |
| Сезон | общий ивент, очки за клики в PvP, таблица лидеров |

Всё состояние лежит в одном объекте `ST.state` и сохраняется в `localStorage`
(ключ `pixel-orca-save-v3`).

## Сервер

```bash
node server/server.js
```

Переменные окружения:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | `8081` | порт HTTP + WebSocket |
| `HOST` | `0.0.0.0` | адрес прослушивания |
| `DATABASE_URL` | — | **если задан — база живёт в PostgreSQL**, см. «PostgreSQL» |
| `DATA_FILE` | подбирается автоматически | файл базы (когда нет `DATABASE_URL`); см. «Где лежит база» |
| `DATA_DIR` | — | каталог базы, к нему добавляется `db.json` |
| `PVP_MS` | `30000` | длительность дуэли |
| `RAID_MS` | `60000` | длительность рейда |
| `TICK` | `250` | период рассылки тиков боя |
| `SEASON_MS` | `30 дней` | длина сезона |

### PostgreSQL

Самый надёжный способ хранить базу: она живёт **вне** сервиса, поэтому
переживает редеплой, пересоздание контейнера и смену платформы — ровно то,
из-за чего страдал файловый режим.

**Включение.** Достаточно задать одну переменную окружения:

```
DATABASE_URL=postgresql://user:pass@host:5432/kosatka?sslmode=require
```

Схему создавать вручную не нужно: сервис на первом старте сам выполнит
`CREATE TABLE IF NOT EXISTS`. Таблицы — `accounts`, `clans`, `meta`
(префикс отсутствует, чтобы не спорить с чужими данными в общей базе).

| Переменная | Смысл |
|---|---|
| `DATABASE_URL` | строка подключения; SSL определяется автоматически для heroku/neon/supabase/render, иначе — по `sslmode=require` |

**Проверка перед деплоем** (создаёт схему, пишет тестовую запись,
перечитывает её новым подключением и убирает за собой):

```
DATABASE_URL='postgresql://user:pass@host:5432/kosatka?sslmode=require' \
  node tools/pg-check.mjs
```

**Что важно знать.**
- Сейв игрока — до 512 КБ, поэтому запись **диффовая**: в базу попадают
  только реально изменившиеся аккаунты и кланы, а не вся база целиком.
- Запись идёт в транзакции; если что-то не пишется, сервер продолжает
  работать, а ошибка видна в логах и в `/api/health` (`dbBackend: "pg"`).
- Ники уникальны на уровне БД (`UNIQUE` по нижнему регистру) — дубликат
  не сохранится даже при гонке.
- `DATABASE_URL` не задан → автоматически включается файловый режим, так
  что локальный запуск и тесты не ломаются.
- **Начальная база пустая.** Файловый `db.json` в PostgreSQL не
  переносится автоматически — переносить старый прогресс нужно отдельно,
  если он нужен.

### Где лежит база

Задай `DATABASE_URL` — и база живёт в **PostgreSQL** (это лучший вариант,
подробности ниже). Если переменная не задана, работает файловый режим.

В файловом режиме база **не должна** находиться внутри рабочей копии:
деплой перезаливает репозиторий и затирает её вместе с аккаунтами и
кланами. Если `DATA_FILE`/`DATA_DIR` не заданы, `server/paths.js` выбирает
первое доступное и доступное для записи место:

| Порядок | Путь | Когда подходит |
|---|---|---|
| 1 | `$DATA_FILE` | задано вручную — приоритет максимальный |
| 2 | `$DATA_DIR/db.json` | задан каталог |
| 3 | `/data/kosatka/db.json` | Render / Railway / Fly, Docker-volume |
| 4 | `~/.kosatka/db.json` | обычный VPS: не нужен root, переживает деплой |
| 5 | `server/data/db.json` | запасной вариант, в логе помечается `← ЭФЕМЕРНО` |

При переходе на новый путь старая база из `server/data/db.json`
переносится автоматически (копия остаётся на месте). Каталог создаётся
сам. Проверить можно в логах при старте или запросом
`GET /api/health`.

**Важно: «постоянный путь» ≠ «постоянные данные».** Если платформа
пересоздаёт контейнер, а каталог базы лежит в слое образа (том не
подключён), база исчезнет при каждом редеплое, какой бы путь ни стоял.
Поэтому в логах и в `/api/health` есть диагностика:

| Поле | Значение |
|---|---|
| `dbBackend` | `pg` — база в PostgreSQL, `file` — в JSON-файле |
| `dbHost` | хост PostgreSQL (только при `dbBackend: "pg"`) |
| `dbSource` | откуда выбран путь: `postgres`, `DATA_FILE`, `DATA_DIR`, `/data`, `home`, `legacy` |
| `dbSameFs` | `true` — база в том же образе, что и код (том не подключён); `false` — отдельный том |
| `dbFirst` | метка первого запуска на этом диске, никогда не перезаписывается |
| `dbPersistent` | путь не внутри репозитория (сам по себе ещё не гарантия) |

Как проверить после редеплоя: сравнить `dbFirst` до и после. Метка на
месте с прежней датой — диск пережил рестарт. Метки нет или дата откатилась
— каталог затирается: нужен подключённый volume платформы (например,
Render Disk → `/data`, Fly Volume → `/data`) либо внешняя БД.

#### Бэкап в репозиторий GitHub (когда тома нет)

Если подключить volume нельзя, база всё равно может переживать редеплой:
сервер складывает снимок в **приватный** репозиторий GitHub, а при старте
с пустой базой поднимает её оттуда. Аккаунты, кланы, лидерборд и сезон
возвращаются как ни в чём не бывало.

| Переменная | Смысл |
|---|---|
| `BACKUP_REPO` | `owner/name` приватного репозитория, например `catmaikl777/kosatka-data` |
| `BACKUP_TOKEN` | fine-grained токен GitHub с правом **Contents: Read and write** только на этот репозиторий |
| `BACKUP_PATH` | файл в репозитории, по умолчанию `db.json` |
| `BACKUP_BRANCH` | ветка, по умолчанию `main` |
| `BACKUP_EVERY_MS` | как часто выкладывать снимок, по умолчанию 5 минут (минимум 30 с) |
| `BACKUP_API` | адрес API, по умолчанию `https://api.github.com` (для GitHub Enterprise) |

Репозиторий обязан быть **приватным**: в снимке лежат хеши паролей и
токены сессий. Токен задаётся только в переменных окружения и уходит
в GitHub заголовком `Authorization`, в логи не попадает.

Как это работает:

* снимок выкладывается при изменении базы (`BACKUP_EVERY_MS`) и всегда
  при остановке сервера (`SIGINT`/`SIGTERM`) — даже если ничего не менялось;
* повторно база выкладывается, только если содержимое отличается от
  прошлого снимка, так что репозиторий не забивается коммитами;
* при старте, если файла базы не было, сервер берёт снимок из репозитория
  и продолжает работу с ним; если снимка ещё нет — просто начинает с нуля;
* ошибка GitHub (нет сети, токен не проходит, репозиторий удалён) **не**
  ломает сервер: причина попадает в `backup.error` в `/api/health`, игра
  продолжает работать, а личный прогресс игрока подтянется с его телефона.

В `/api/health` появится:

```json
"backup": { "on": true, "last": "2026-09-28T18:00:00.000Z", "error": null,
            "pushes": 12, "restores": 1 }
```

`restores: 1` означает, что сервер поднялся с пустым диском и база была
восстановлена из репозитория. Проверить сценарий целиком можно локально:
`npm run test:backup` поднимает фейковый GitHub, дважды «стирает» базу и
убеждается, что аккаунт выживает.

HTTP-эндпоинты: `GET /` (статика, если положить клиент рядом), `GET /api/health`
(состояние: игроки, аккаунты, кланы, лобби, команды, остаток сезона).

### Протокол

Клиент шлёт JSON-сообщения `{ t, rid, ... }`, сервер отвечает `{ t, rid, ... }`.
`rid` — идентификатор запроса (данные не должны его затирать), ответы на запросы
повторяют `rid`, события приходят без него.

Основные типы сообщений:

```
auth:register  auth:login  auth:logout  resume
save  load
lb  clans  clan:create  clan:join  clan:leave  clan:delete  clan:donate
pvp:lobbies  pvp:create  pvp:join  pvp:joinCode  pvp:ready  pvp:leave  pvp:clicks
raid:teams  raid:create  raid:join  raid:leave  raid:search  raid:clicks
event:info
```

Ошибка приходит как `{ t: '<тип>:err', rid, msg }` и превращается в `Error` с этим
текстом. Сервер ограничивает поток (40 сообщений/сек, 200 для кликов боя) и отвечает
ошибкой, а не молча роняет запрос.

## Тесты

```bash
node tools/checkclient.mjs     # статическая целостность клиента
node tools/checksprites.mjs    # спрайты и палитра
node tools/smoke-client.mjs    # клиент в мини-DOM: клики, магазин, квесты, сейв, офлайн
node tools/smoke-server.mjs    # сервер напрямую: 3 клиента, PvP, рейд, кланы
node tools/smoke-pg.cjs        # PostgreSQL-хранилище: дифф-запись, индексы, откат
node tools/pg-check.mjs        # живая проверка твоей БД (нужен DATABASE_URL)
node tools/smoke-backup.mjs    # бэкап базы: wipe → восстановление → вход
node tools/smoke-balance.mjs   # регресс темпа прохождения
node tools/smoke-online.mjs    # сквозной: настоящие js/*.js против живого сервера
```

`smoke-online.mjs` поднимает временный сервер на случайном порту, подключает несколько
настоящих клиентов через native WebSocket и проверяет весь путь: регистрация, облачный
сейв, авто-вход по токену, кланы, живой PvP с кликами, рейд 3×3 с общим счётом,
сезонный ивент и поведение клиента при падении сервера. Тест самодостаточен:
подбирает свободный порт, чистит за собой сервер и временную базу.

Диагностика: `PO_SRVLOG=1 node tools/smoke-online.mjs` — печатает лог сервера;
`PO_QUEST=2 node tools/smoke-client.mjs` — меняет объём прогонов офлайн-теста.

### Баланс

```bash
node tools/balance.mjs                  # таблица текущего темпа (день, уровень, доход)
node tools/balance.mjs --first 30       # первые покупки: как быстро растёт старт
node tools/balance.mjs --search         # перебор параметров под нужные вехи
```

`balance.mjs` грузит боевые `js/data.js` + `js/state.js` в Node, сажает виртуального
игрока (5 кликов/сек, комбо 50, час в день, оффлайн 23 ч) и покупает улучшения по
выгоде на монету. Печатает вехи (уровень 100, 1e9 монет, 1e6 кликов, «всё выкуплено»)
и интервалы между покупками: p50, p90, худшее ожидание.

Два правила, без которых экономика ломается (проверяет `smoke-balance.mjs`):

* **`max` у каждого улучшения и `MAX_LEVEL`.** Пока бонусы растут бесконечно, доход
  обгоняет цену любого улучшения и игра выкупается за час. С пределами у прохождения
  появляется финал, а числа остаются конечными.
* **`growth` заметно больше `val`.** `growth/val` — во сколько раз дольше копится
  следующий уровень. Условие `growth ≈ val` даёт вечный режим, `growth` сильно выше
  `val` — стену через пару часов.

Текущие ориентиры: полное прохождение на 195-й день, уровень 100 на 7-й,
`MAX_LEVEL` на 35-й, доход выходит на плато ~6.9M/сек.

## Деплой

Схема: **фронтенд — статика на GitHub Pages**, **бэкенд — процесс на PaaS с WebSocket**.
Всё нужное для этого лежит прямо в репозитории: `Dockerfile`, `render.yaml`, `fly.toml`,
`Procfile`, `.env.example` и воркфлоу `.github/workflows/pages.yml`.

```
GitHub Pages  ──── https://catmaikl777.github.io/kosatka/
   (index.html, css, js, img, sw.js)          статика, ~250 КБ
        │  wss://
        ▼
PaaS (Render / Fly / Railway)  ──── WebSocket /ws + /api/health
   (server/server.js, база на постоянном диске)
```

Один адрес настраивается в одном месте — `js/config.js`, поле `server`.
Его меняет сборочный скрипт, руками править не нужно.

### Шаг 1. Бэкенд на PaaS

**Render (самый простой путь).** New → Blueprint → укажи репозиторий. Всё уже описано
в `render.yaml`: план, регион, health-check и **диск на 1 ГБ**. Free-план брать нельзя:
через 15 минут простоя сервис засыпает и обрывает живые бои.

**Fly.io.**
```bash
fly volumes create kosatka_data --size 1
fly deploy
fly secrets set PUBLIC_URL=https://kosatka.fly.dev
fly scale count 1        # больше одной машины нельзя: лобби живут в памяти процесса
```

**Railway.** New Project → Deploy from repo (Dockerfile подхватится сам) → добавь
Volume на `/data`. Start command не нужен, но можно задать `node server/server.js`.

**Что обязательно настроить:**

| Переменная | Значение | Зачем |
|---|---|---|
| `DATA_FILE` | `/data/db.json` | путь на **постоянном** диске |
| диск/volume | `/data` | без него аккаунты и кланы пропадают после каждого деплоя |
| `PORT` | платформа подставит сама | не переопределяй |
| `HOST` | `0.0.0.0` | слушать все интерфейсы |
| `PUBLIC_URL` | `https://<app>.onrender.com` | только для лога при старте |

Проверка, что бэкенд жив:
```bash
curl https://<app>.onrender.com/api/health
# {"ok":true,"uptime":42,"players":0,"accounts":3,...}
```

### Шаг 2. Фронтенд на GitHub Pages

Сайт: **https://catmaikl777.github.io/kosatka/**

1. **Settings → Pages → Build and deployment → Source: GitHub Actions**.
2. **Settings → Secrets and variables → Actions → Variables** → добавить `PO_SERVER_URL`
   со значением `wss://<app>.onrender.com/ws` (именно Variables, не Secret).
3. Ветка `main` уже настроена: пуш в неё собирает и публикует сайт.

Что происходит при пуше: `prepare-pages.mjs` копирует в `dist/` только браузерные файлы,
подставляет `PO_SERVER_URL` в `js/config.js`, пересобирает список precache в `sw.js` и
проверяет, что в сборке нет битых ссылок и абсолютных путей; воркфлоу публикует `dist/`.

Если задеплоить вручную (без Actions):
```bash
node tools/prepare-pages.mjs wss://<app>.onrender.com/ws
node tools/serve-pages.mjs       # локально посмотреть ровно то, что уедет на Pages
```

### Шаг 3. Проверка перед боем

```bash
npm test                          # клиент + сервер + живой сквозной прогон
npm run test:dist                 # те же живые тесты, но на собранном dist/
```

В браузере на странице GitHub Pages должно быть: в HUD — «онлайн» вместо «офлайн»,
в консоли `new WebSocket('wss://…/ws')` со статусом 101, а вкладка Network — один
долгий WebSocket-запрос к бэкенду.

### Частые грабли

- **Сайт открылся, но «офлайн».** Не задана `PO_SERVER_URL` либо в ней `http://`
  вместо `wss://`. Проверь `dist/js/config.js` — там должен быть адрес.
- **Страница перестала грузиться после деплоя.** Залипший service worker: обновить
  с очисткой (в DevTools → Application → Unregister) или подождать смены версии кэша.
- **Обрывы боёв на Render free.** Нужен платный план, иначе сервис спит.
- **Всё пропало после рестарта.** Не смонтирован диск под `DATA_FILE`. Надёжное
  решение — задать `DATABASE_URL` и уйти на PostgreSQL.
- **`[db] не удалось открыть базу`.** Проверь строку подключения и что из
  контейнера до неё долетает сеть; подробности — `node tools/pg-check.mjs`.
- **404 на `/ws`.** Прокси не пробрасывает `Upgrade` — на Render/Fly/Railway это
  работает из коробки, за nginx нужен `proxy_set_header Upgrade $http_upgrade;`.
- **Две реплики бэкенда.** Лобби, рейды и аккаунты живут в памяти процесса,
  вторая машина = второй параллельный мир. Масштабировать только вертикально.

```
  index.html            разметка, HUD, окна
  sw.js                 service worker: офлайн-кэш оболочки
  manifest.webmanifest  PWA-манифест (установка на телефон)
  .nojekyll             чтобы Jekyll на Pages не выкинул файлы
  css/pixel.css         пиксельный UI
  js/config.js          адрес WebSocket-сервера — единственное место для деплоя
  js/state.js           состояние, формулы, сейв, престиж
```
